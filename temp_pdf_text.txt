The primary care benefit package or most commonly referred to as the PCB1 was implemented last 2012 replacing the outpatient benefit package at the time as denoted in PhilHealth Circular No. 10 s-2012 "Implementing Guidelines for Universal Health Care Primary Care Benefit I (PCB1) Package for Transition Period CY 2012-2013. The said circular initially covers members under the Sponsored Program, Organized Group and Overseas Workers Program to avail of the services through the Rural Health Units.

In October 2018, the PCB1 benefit package was expanded to members under the formal economy (private and government employees), senior citizens and lifetime members thru the PhilHealth Circular No. 17 s2018. And with the Corporation remaining true to its mandate of providing health insurance coverage and ensure affordable, acceptable, available and accessible healthcare services for all citizens of the Philippines, the PhilHealth Konsulta Benefit Package integrates the existing Primary Care Benefit I (PCB1) and expanded Primary Care Benefit 1 (ePCB) that shall be made available for all Filipinos.

To ensure ease of availment at the point of care for all its beneficiaries, PhilHealth has partnered with existing electronic medical record (EMR) providers to automate the submission of reporting requirements necessary for the processing of provider payments. Said venture has been established through the issuance of PhilHealth Advisory 2016-0040 introducing the implementation of Electronic Medical Records for the Primary Care Benefit by January 1, 2017.

Being that more data will be required from the Konsulta providers for the Konsulta implementation, PhilHealth will be opening direct transmission of Konsulta data which will integrate or be similar with the eClaims architecture. Among the list of services which will be offered to Konsulta providers and service providers are as follows:

 Phase I: Authentication of Application o Get Token Method (GTM)

 Phase II: Konsulta Registration Validation o Member/Dependent Registration Check (MDRC) o Extract Registration List (ERL) o Authorization Transaction Code Validation (ATCV)

 Phase III: Konsulta Reporting o Validate Konsulta Report (VER) o Submit Konsulta Report (SER)

Republic Act 8792 or the e-Commerce Act was signed into law on June 14, 2000, and mandated all government agencies to, among others, transact government business and perform government functions using electronic data messages or electronic documents. It therefore provides for the legal recognition of electronic documents, data messages, electronic signatures and electronic contracts. RA 8792 provides the legal framework and environment for the PhilHealth Konsulta environment. The Konsulta Benefit Package shall be included in the PhilHealth Konsulta environment to provide an efficient and effective reporting and processing of availment for the primary care benefit. The Konsulta system shall introduce the following features, to wit: 1) a paper-free transaction through a fully electronic and/or online submission of Konsulta report by accredited health providers; 2) online evaluation and processing of Konsulta in PhilHealth Regional and Service offices; and 3) online tracking or status verification of Konsulta availments. This document applies to accredited Konsulta health care providers and Service Provider (SP), which will serve as conduits between PhilHealth and the HCPs and HCIs with in-house software solutions, which will provide utilities to enable access to the PhilHealth Konsulta API or PKA.

ABOUT THE SOFTWARE CERTIFICATION ID Starting with version 1.0 of PKA, all applications that will access the said services shall be required to be certified by PhilHealth. Each certification is targeted for a specific version of PKA. To check whether an application calling a service method of PKA is certified, the calling application should indicate the Software Certification ID issued by PhilHealth after an application has been certified.
USE OF ACCESS TOKEN Access tokens are used in token-based authentication to allow an application to access PKA. The application receives an access token after a user successfully authenticates and authorizes access, then passes the access token as a credential when it calls the target service method. Each method call will require token included in the header request. In the header request, use "Token" for the key and the generated access token for the value.
ENCRYPTION AND DECRYPTION OF THE XML PAYLOAD DATA For added security measures, starting with version 1.0 of PKA, HCI applications should encrypt all input parameters that are to be encoded as XML text. HCI applications should also decrypt all output parameters that are returned in XML format. Please refer to the "Guidelines for the Encryption and Decryption of XML" included in the development kit.

4. CONFIDENTIALITY
Given the nature PhilHealth mandate, it is vital that we maintain the confidentiality of patient information. PhilHealth is committed in ensuring utmost confidentiality of health records and related information of all patient because the right to privacy is personal and fundamental; likewise it is the responsibility of PhilHealth to safeguard all confidential information.
Confidential Information
Confidential information includes, but is not limited to, protected health information, personal financial information, patient records, or information gained from committee meetings, hospital or facility visits during accreditation and investigation, inquiries from members, patients or other PhilHealth employees. Example include: data contained on claim forms, past and current medical and psychiatric record member employment data, patient insurance and billing of records, computerized patient data, visual observation of patients/members or any verbal information provided by or about a patient. These information may be contained via any communication medium, including verbal, written or electronic. 1
Protection Policies and Procedures
All information that can be used to identify a Patient or a commercial entity in a commercially sensitive context is considered Confidential Health Information (CHI).
It is required that all partners develop, institute, educate staff and periodically update standard operating policies and procedures that protect CHI. The policies and procedures must be available for inspection and their use must be demonstrate upon request. PhilHealth will make available default policies and procedures.
Necessary and authorized access. Each party is required to ensure that only minimum necessary personnel have access to CHI. Additionally, each party must have appropriate means to secure CHI and its use within its operations including when exchanging CHI with other partners. Each party must provide a means to authenticate authorized users.
Unauthorized access. Every party should keep CHI from unauthorized access. PhilHealth must be notified, however, as soon as unauthorized access is detected. This notice must include what was disclosed, how it was obtained (means and methods), who gained unauthorized access if known, if the data has been subsequently unlawfully disclosed and the risk mitigation plan the party is now pursuing to prevent any further unauthorized access. Confidentiality breaches can occur from external and internal sources. Each party must have a published sanction policy and ensure that is effectively communicated to staff periodically. For external breaches appropriate law enforcement officials will be involved in the investigation and prosecution as necessary.
Storage of CHI. Each party is required to develop, maintain and implement policies and procedures for protecting CHI stored electronically or via paper. This is especially true for off-site storage in the case of paper records and back-ups, archives and live storage of electronic records. The storage policies and procedures apply irrespective of the purpose of storage, for instance whether the CHI is stored on a CD for archiving or transmission purposes.

ANNEX D: GUIDELINES FOR THE ENCRYPTION AND DECRYPTION OF XML
GUIDELINES AND PROCEDURES
 The application of HCI should encrypt input parameters that are supposed to be passed as XML. HCI applications should also decrypt all the output parameters that are supposed to be returned by PKA as XML.
 The input and output parameters that are to be passed as XML text will be referred in this section as XML payload data.
ENCRYPTION OF THE XML PAYLOAD DATA
1. The procedures for the encryption of the XML payload data will be similar to the procedures in the encryption of the image files of the supporting documents of electronically submitted claims. The difference is that encryption of the XML payload data will not use public-key encryption.
2. The XML payload data will be encrypted using "AES-256-CBC" algorithm. 3. PhilHealth will issue the passphrase/password/cipher key to be used by each HCI. The password
should be hashed using SHA-256 algorithm. The first 32 bytes of the hashed value should be passed as the password for the AES encryption. If the resulting hashed value is less than 32-bytes, the value should be padded with `0x00' or null character. 4. An array of random 128 bytes should be used as the initialization vector. 5. Before encrypting the data, compute for the hash of file using SHA-256 hash method. (This hash will be compared to the hash that will be computed later after the file has been extracted on from decrypted file on PhilHealth side. If the hash values match, it assures that the file has been encrypted 6. The expected output of these encryption procedures is to be encoded in JSON. The figure below shows the expected key-value pairs that are to be included in the JSON text.
a. The "docMimeType" key, should have fixed value of "<text/xml>". b. The value for the "hash" item is the computed hash of the raw unencrypted XML text using
the SHA-256 hash algorithm. c. The value for "key1" should be an empty string. d. The value for "key2" should also be set to empty string. e. The value for "iv" key should be the base-64 encoded value of the initialization vector
mentioned in Step#6. f. The value for the "doc" key should the base-64 encoded value of the result of the AES-256
encryption of the XML payload data.
{ "docMimeType": "<text/xml>", "hash": "<SHA-256 hash of the XML text (before encryption)>", "key1" : "", "key2" : "", "iv" : "<Encoded in Base64 format, the public key encrypted initialization vector>", "doc" : "<Encoded in Base64 format, AES-256-CBC encrypted image file data> }
Figure 1: Format/Layout of encrypted data
7. SPs/HCIs may use their preferred programming language or tools in doing the encryption and decryption. The development kit includes sample codes in C# and PHP. For the sample source codes
Page 49

in PHP, the encryptXmlPayloadData method of the PhilHealthEClaimsEncryptor class contains an implementation of the encryption procedures outlined above.
DECRYPTION OF THE XML PAYLOAD DATA
The decryption process is just the reverse of the encryption process outlined in previous section.For the service methods that are supposed to return an XML, PKA will encrypt the supposed XML data and return a text encoded in JSON whose key-value pairs as described in the previous section.
1. After receiving the JSON text, the HCI application should parse it. 2. Get the value of the "iv" key. That is the base-64 encoded value of the initialization vector used in
the AES-256 encryption of the XML payload data. Decode the value of the initialization vector from base-64 encoding to its corresponding raw array of bytes. 3. Get the password, passphrase or cipher key of the HCI. 4. Get the SHA-256 hash value of that value. . If the length in bytes of the resulting hashed value is less than 32, pad the value with `\0'' or null character. 5. Get the value of the "doc" key. That value is the base-64 encoding of the encrypted data. Decode the data from base-64 encoding to the raw array of bytes of the encrypted data, With values of the passphrase, initialization vector and actual encrypted data, decrypt the data using AES-256CBC. 6. You may get the hash value of the decrypted data and compare it with the value of the "hash" key. 7. After the decryption, the application of HCI may now process and parse the target XML data. SPs/HCIs may use their preferred programming language or tools in doing the encryption and decryption. The development kit includes sample codes in C# and PHP. For the sample source codes in PHP, the decryptPayloadDataToXmlmethod of the PhilHealthEClaimsEncryptor class contains an implementation of the decryption procedures outlined above.
